# Where USD import time goes

Loading the Moana Island scene took over fifteen minutes and used one
core. This is what the importer actually spends its time on, which parts
of that crust owns, and what happened when the rest was attacked anyway.

Numbers are from a 4-core box, Rust stable, `--release`, min of three
runs, reported by `--stats`. The scenes are generated by
`scripts/gen_moana_like_scene.py` and the two throwaway generators quoted
below; none are checked in (they are 5–100 MB of text).

## The three cost centres, isolated

Moana is not one performance problem but three, and a real stage mixes
them. Each was isolated into its own synthetic stage:

| stage | what it stresses | shape |
| --- | --- | --- |
| `primheavy` | prim count | 200k empty `Xform` prims |
| `geoheavy` | unique geometry | 600 mesh prims, 1M unique triangles |
| `instheavy` | instance placements | one `PointInstancer`, 2M placements |

| phase | primheavy | geoheavy | instheavy |
| --- | --- | --- | --- |
| Open stage | 0.46s | 0.93s | 0.53s |
| Traverse prims (before) | 14.34s | 2.21s | 0.31s |
| Traverse prims (after) | 13.51s | **0.59s** | 0.33s |
| Commit acceleration structure | 0.00s | 0.00s | 2.27s |

The middle column is what this work bought: **3.7x** on the phase that
turns authored meshes into kernel geometry. The other two columns are
where the remaining time lives, and they are discussed below.

## Geometry building: was serial, now parallel (3.7x)

Reading a mesh out of USD is cheap. The `usd_probe` example walks a stage
doing progressively more per prim, and reading *every* array of
`geoheavy` — 1.56M points and 3M faces — costs 14 ms, because a `.usda`
layer's values are decoded when the stage opens (a `.usdc` layer's are
decompressed per read, and measured no slower here). Essentially all of
that 2.21s was crust's own work on the traversal thread: hashing the
arrays for the dedup cache, fan-triangulating, and building each mesh's
BVH one mesh at a time.

The traversal itself cannot be parallelized (see below), but nothing it
*produces* has to be built on it. `GeometryQueue` in `usd_import.rs` is
that seam:

- a queued build returns a `SceneSlot` — an index, not a scene;
- `flush()` builds every outstanding slot with `rayon`;
- attachments are buffered and drained **in traversal order**, so every
  `geom_id` is what a serial importer would have assigned, which matters
  because an `AreaLight` records the id of its own surface;
- batching is bounded on both sides — 128 MiB of un-built geometry and
  8192 buffered attachments — so peak memory does not grow with the
  scene, and an attachment that waits on nothing at all is passed
  straight through (the path a dense `PointInstancer` takes for millions
  of placements).

The one place the importer has to look *inside* a slot is a
`PointInstancer` nested in a prototype, which builds a sub-scene of the
inner geometry; that forces a flush, and nested instancers are rare
enough for it not to matter.

`MeshKey`'s content hash was also costing more than the dedup it enables:
`DefaultHasher` is SipHash-1-3 and was fed one `write_u32` per
coordinate, over every point of every mesh prim *including* the
duplicates it exists to detect. It is now a four-lane xxHash64 mixer,
deterministic across runs and platforms, about 5x the throughput. Mesh
identity is still decided by the digest plus the array lengths, never by
comparing the arrays — dedup trusts 64 bits not to collide, which is why
the mixer's quality matters more here than its speed.

## Per-prim queries: ~20 composed lookups, now ~5

Every composed query on an openusd `Stage` is a `HashMap` lookup keyed by
a `String` path, and the importer was asking many more of them than it
needed:

- the schema dispatch tried `Mesh::get`, `Sphere::get`, `Camera::get`,
  … down a chain of ten, each of which re-read and re-allocated the same
  composed `typeName`. It now reads the type once and matches on it
  (`PrimKind`);
- `resets_xform_stack_at` tried up to six schema `get()`s to find an
  `Xformable` view of the prim, then read `xformOpOrder` — which
  `compose_xform_ops` had just read. Both answers now come from that one
  read. As a side effect the reset applies to *every* prim rather than
  only those six types, which is what UsdGeomXformable actually
  specifies, pinned by `reset_xform_stack_applies_to_any_prim_type`;
- the `crust:volume:type` probe ran on every prim. It now runs only on
  prims whose type does not already say what they are — a volume is
  authored on a `Cube` or a bare `Xform`/`Scope`, as both sample scenes
  do.

On `primheavy` this is worth ~6% (14.34s → 13.51s). It is small because
of what the other 94% turns out to be.

## What is not ours: openusd's composition engine

Instrumenting the traversal loop on `primheavy` (200k empty Xforms, no
geometry at all, 68 µs per prim):

| section | time | share |
| --- | --- | --- |
| `is_abstract()` | 9.37s | 71% |
| `children()` | 2.72s | 21% |
| everything else the importer does | 1.02s | 8% |

`is_abstract()` is not expensive; it is merely the *first* composed query
on each prim, and so pays for building that prim's composition index.
`children()` is 13 µs per prim because `compute_prim_child_names` is
recomputed on every call rather than cached. Both are inside openusd
0.5, which composes on an `Rc`/`RefCell` stage — the crate's own source
carries a `TODO(rayon)` at exactly this boundary.

### Giving each thread its own stage makes it slower

`Stage` cannot be shared across threads, but each thread can open its
own and compose a disjoint slice of the namespace. The
`usd_parallel_probe` example does that — breadth-first split of the
namespace into 8x more work items than threads, a work-stealing counter,
one `Stage::open` per worker:

| threads | wall clock | speedup |
| --- | --- | --- |
| 1 | 9.69s | 1.00x |
| 2 | 16.18s | 0.60x |
| 4 | 28.30s | 0.35x |

Each worker walking a *quarter* of the prims takes three times longer
than one worker walking all of them. It is not CPU quota (a pure-compute
loop scales 4/4 on this box) and it is not simple allocator contention (a
`HashMap<String, _>` churn benchmark scales fine); it is that composition
retains a large, pointer-chasing, freshly-allocated working set —
~2.7 KB per prim — and this box's memory subsystem loses about half its
throughput at four such threads. The approach also multiplies the
composition cache by the thread count, which is the wrong trade for the
one scene it is meant to help.

So the probe stays in the tree as a measurement, not as a feature.

### Which leaves the reader itself

Crust is pure Rust and that is not negotiable, so binding the C++
OpenUSD — whose composition engine really is threaded — is off the table,
and so is any replacement reader that is not itself pure Rust. The route
is a fork of `openusd` (0.5.0 is still the latest release as of
2026-06-08), measured with `usd_probe` and upstreamed.

Worth saying plainly before anyone reaches for threads there: **46 µs to
compose one empty `Xform` on a flat, single-layer stage is one to two
orders of magnitude off what composition should cost.** The constant
factor is the bug; the serialism is a symptom of it, since it is the
allocation volume that makes per-thread stages lose to a single one.
Ranked by payoff over risk:

1. **Cache `compute_prim_child_names`.** `PrimIndexRef::child_names`
   recomputes it per call — 13 µs/prim, ~21% of the traverse — and the
   cache would sit next to the `indices` map it already has.
2. **Stop allocating paths.** `sdf::Path` is a `String`, so every cache
   lookup hashes a path and every derived path (`prim_path()`,
   `append_path`, `effective_path`) allocates a new one. Interning is the
   broad fix for the 46 µs and makes everything downstream cheaper.
3. **`anchor_asset_paths` re-runs `Resolver::resolve` — a filesystem hit
   — on every asset-path read** (its own `TODO(perf)`). Invisible on a
   synthetic single-layer stage; potentially large on a scene built from
   references, which is exactly the Moana shape.
4. **Then, and only then, `Rc` → `Arc` with a concurrent index map** —
   the crate's `TODO(rayon)`. It is pervasive, and the numbers above say
   it does not pay until 1–3 land.

## Committing the top-level BVH

`instheavy` spends 2.27s there for 2M instances. The build itself
parallelizes well (5.02s on one thread, 1.34s on four — 3.9x), and two
allocation costs around it were removed: `SceneBuilder::commit` sized its
primitive table by doubling (re-copying every `PrimNode` written so far
at each step), and the BVH build's `merge` concatenated each child's
finished arrays into its parent, which copies a node once per level above
it *on the parent thread, immediately after `rayon::join`*. `Subtree` is
now linked and laid out once by `flatten`, in the same order, so the flat
tree is byte-for-byte unchanged. On four cores that second change is only
worth 2–3%; it is in because the copy sat on the serial side of Amdahl,
where its share grows with core count.

What is left there is the SBVH itself — binned object splits plus spatial
splits over millions of references — and `collapse`, a 0.85s sequential
layout pass over 2.4M nodes that has not been touched.

## Diagnosing a specific scene

`--stats` splits the load into the phases above, so a slow stage says
which of the three problems it has:

```bash
cargo run --release -- -i island.usd --stats -s 1
```

- **Open stage** dominant → layer parsing, inside openusd. A `.usda`
  stage decodes every value up front; converting to `.usdc` moves that
  cost to first read (`cargo run --release -p crust-core --example tousdc
  -- in.usda out.usdc`).
- **Traverse prims** dominant, with **Build geometry** a small part of it
  → prim-count bound, i.e. openusd composition. Nothing crust-side left.
- **Build geometry (parallel)** dominant → unique geometry volume; scales
  with cores.
- **Commit acceleration structure** dominant → instance/primitive count.
- **peak memory (RSS)** near the machine's RAM → the real problem is
  paging, and the `unique` vs `top-level` primitive counts say whether
  instancing is collapsing the scene as it should.
